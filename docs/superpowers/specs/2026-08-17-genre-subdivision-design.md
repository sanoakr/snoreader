# ジャンルのサブジャンル分割 — 設計

## 背景・目的

サイドバーのジャンル別未読件数が大きくなると、その束を片付ける気が起きなくなる。実測（2026-08-17）では 1 日のうちに `AI・LLM 66` / `開発・技術 51` まで伸び、同日夕方の時点でも以下だった。

```
ai 42  dev 34  politics 25  science 20  economy 20  life 16  culture 16  other 15
```

未読を捨てる導線（まとめて既読・まとめて非表示）は 2026-08-08 のジャンルトリアージで用意済みだが、束が大きすぎると「中身を確認せずに 42 件を捨てる」か「1 件ずつ開く」の二択になり、どちらも実行されない。

そこで **ジャンルに子階層を持たせ、親の未読が閾値を超えたときだけ子を展開して、ひとつの束を小さく見せる**。目的は件数の上限を機械的に守ることではなく、「これだけなら片付けられる」と思える大きさの束を提示することにある。

閾値は **30**（`GENRE_SPLIT_THRESHOLD`）。

## 設計上の前提（実測で確定した事実）

### 1. タグ由来の分割では「必ず 30 以下」を保証できない

未読記事について「そのジャンルに決めた原因タグ」の分布を数えた。

| ジャンル | 未読 | 決定タグ |
|---|---|---|
| AI・LLM | 42 | **`ai` 32**, `llm` 9, `claude` 1 |
| 開発・技術 | 34 | `programming` 9, `aws` 4, `tools` 3, `hardware` 3, (該当なし) 3, `cloud` 2, `database` 2, `windows` 1 |
| 政治・行政 | 25 | `government` 9, `politics` 5, `policy` 2, `labor` 2, `disability` 2, `law` 2, … |

AI・LLM はジャンル名と同名の支配的タグ `ai` が 32/42 を占める。タグで割っても 32/9/1 にしかならず、全体が 66 件だった時期には `ai` の束だけで 50 件前後になる。**分布が偏っているジャンルでは、意味による分割で上限を保証することは原理的にできない。**

したがって本設計は上限を保証しない。子が閾値を超えたときは警告色で示し、辞書を育てるのは手動とする。

### 2. 代表タグを子に降ろさないと数字は減らない

`ai` タグを親に残したまま `llm` 系だけを子にすると、親側に 27 件（42 件中）が残り、最大の束は分割前とほぼ変わらない。**子は親のタグを全て引き取り、親を純粋な入れ物にする**のが前提。実データで検証した結果が以下で、親に残る記事は 0 件になり、どの子も 30 以下に収まる。

| AI・LLM | 全記事 | 未読 | | 開発・技術 | 全記事 | 未読 |
|---|---|---|---|---|---|---|
| AI 全般 (`ai`) | 2,880 | 24 | | プログラミング | 672 | 15 |
| LLM・生成AI | 893 | 18 | | クラウド・インフラ | 348 | 7 |
| AI ハードウェア | 5 | 0 | | ツール・ハード | 277 | 6 |
| （親に残る） | 0 | 0 | | 技術一般 | 1,141 | 3 |
| | | | | データ・DB | 192 | 2 |
| | | | | （親に残る） | 0 | 0 |

### 3. 並び順による機械的な分割は一括操作と両立しない

「1〜30 件目 / 31〜60 件目」のような位置による分割は上限を保証できるが、新着が入るたびに束の中身が変わる。`dismiss` が返した ids で戻す Undo（`routers/articles.py` の dismiss）や「その束が該当記事を漏れなく含む」前提が崩れるため採らない。日付範囲であれば境界は動かないので候補になるが、本設計では意味による分割を選んだ（下記「棄却した代替案」）。

### 4. 子キーへの移動は約 15 秒かかる

記事は 17,387 件で全件が `tag_suggestions` を持ち、うち `ai`/`dev` が 6,408 件。この 6,408 件の `genre` を書き換える実測は **14.8 秒**（トランザクションをロールバックして計測）。`articles` のどの列を更新しても FTS トリガーが本文を再インデックスするため（`content` 合計 94MB）、行数に比例して重くなる。

一方 `GET /articles/genres` の集計スキャンは 3 列だけを読むので **0.16 秒**。読み取りは軽く、重いのは書き込み側だけである。

CLAUDE.md が記録している「約 3,000 件で約 47 秒」と比べると 1 行あたりは速い（15.7ms/行 → 7.0ms/行）が、桁は同じで行数に比例する。計測条件が違う可能性があるので、実装時は投入前に同じロールバック計測をやり直して見積もること。

### 5. 分類は決定的な辞書写像のまま

2026-08-08 の設計の前提（LLM は記事をまたいだ語彙の一貫性を保てず、実測で出現回数の 73% が語彙外）は変わらない。子階層も辞書で表現し、LLM は関与しない。

## スコープ

**含む**: `genres` の親子関係、子孫優先の解決規則、階層化した件数 API、親フィルタの子孫展開、親直下だけを選ぶ導線、サイドバーの自動展開と警告表示、推奨サブジャンルの冪等な投入、ジャンル管理 UI での子の作成・移動。

**含まない**: 3 段以上の階層、日付やフィードによる自動分割、子の自動学習（どのタグを子に置くかを利用実績から提案する類）、閾値のユーザー設定。

## データモデル

`genres` に 1 列追加する。`create_all` は既存テーブルを変更しないので、`main.py` lifespan の手動 `ALTER TABLE` 群に追加する。

```
genres.parent_id INTEGER NULL REFERENCES genres(id)
```

- `parent_id IS NULL` が親、値を持つものが子。**階層は 2 段固定**で、子を親に指定する作成・更新は 400 を返す
- 親を削除するときは子も一緒に消える（`ON DELETE CASCADE` 相当を ORM の関係で表現し、削除後に `reclassify_all`）
- `Article.genre` は今と同じ 1 列で **葉のキー**を持つ。子ルールに当たれば子キー、親のルールに当たれば親キー
- `GenreRule.tag` のグローバル一意は維持する。1 タグは 1 ジャンル（親か子のどちらか）にだけ属する
- 既存データの移行は不要。既存の `genre='ai'` は「AI・LLM 直下」として有効なまま

「タグを子に降ろす」は、既存の「既存タグのルールを別ジャンルに付け替える」（`routers/genres.py` は 409 ではなく再割り当てを返す）と同じ操作で行える。

## 分類器

`classify()` は現状「hit したジャンルのうち priority 最小」を選ぶ。階層では**これだけでは分割されない**。`ai`（親を指す）と `llm`（子を指す）が両方 hit したとき、priority の手動調整に頼ると代表タグが親に残り続ける。

解決規則を次の順にする。

1. 通常ルールの hit を集める（無ければ `is_generic` ルール、それも無ければ `other`）
2. hit の中に**祖先・子孫の関係にある組**があれば、子孫を残して祖先を落とす
3. 残った候補から priority 最小を選ぶ。同値は key の辞書順

2 は「より具体的な指定が勝つ」という一文で説明できる規則で、無関係なジャンル同士の優劣は従来通り priority が決める。`GenreRules` スナップショットに `parent: dict[str, str | None]`（子 key → 親 key）を追加して純関数のまま実装する。

**兄弟同士は同順位になる。** 子には親と同じ priority を与える（そうしないと他ジャンルとの優劣が親のときから変わる）ので、同じ親の子は必ず 3 の同値解決＝キーの辞書順で決まる。したがって「受け皿」の子——親の代表タグを引き取る子——には、具体的な兄弟より後にソートされるキーを付ける必要がある。付け忘れると具体的な兄弟の記事まで受け皿に入り、分割の意味が薄れる。`ai` の受け皿を `ai_misc` にしているのはこのため（`ai_infra` < `ai_llm` < `ai_misc`）。汎用ルールしか持たない受け皿（`dev_general` の `technology`）は通常ルールの兄弟と同じ段で競合しないので、この制約を受けない。

`OTHER_GENRE`（`"other"`）は `genres` に行を持たない予約キーのままで、親としても子としても扱わない。

## API

### 件数（破壊的変更）

`GET /articles/genres` を階層で返す。フロントの型（`GenreCount`）も同時に更新する。

```json
[
  {"genre": "ai", "label_ja": "AI・LLM", "unread_count": 42, "direct_count": 0,
   "children": [
     {"genre": "ai_misc", "label_ja": "AI 全般", "unread_count": 24, "direct_count": 24, "children": []},
     {"genre": "ai_llm", "label_ja": "LLM・生成AI", "unread_count": 18, "direct_count": 18, "children": []}
   ]},
  {"genre": "dev", "label_ja": "開発・技術", "unread_count": 34, "direct_count": 0, "children": [...]}
]
```

- `direct_count` はそのキーが直接付いた記事数、`unread_count` は `direct_count` + 子の合計
- 集計クエリは現状の `group_by(Article.genre)` 1 本のまま。畳み込みは Python 側で行い、0.16 秒の読み取り経路を重くしない
- 並びは親を件数降順、子も件数降順
- 親の順序に `other` を含める扱いは現状のまま

### 記事一覧と一括操作

genre スコープの意味を 1 つのヘルパに集約し、`GET /articles` / `POST /articles/mark-all-read` / `POST /articles/dismiss` が共有する。

- `genre=ai` → **`ai` とその子孫すべて**（`Article.genre IN (...)`）
- `genre=ai_llm` → そのキーだけ
- `genre=ai&genre_exact=true` → **`ai` 直下だけ**（子を含まない）

`genre_exact` は、子を持つ親の「まだ子ルールが無いタグの記事」を単独で処理するために必要。これが無いと未分類の残りは親ごと（=子も巻き込んで）しか操作できない。キー集合は決定的なので「その束が該当記事を漏れなく含む」性質は保たれる。

### ジャンル定義の編集

既存の `routers/genres.py` の CRUD に沿う。

- `POST /genres` は `parent_id` を受け付ける。親が既に子である場合は 400
- `PATCH /genres/{id}` で親の付け替えを許す。自分自身・自分の子孫を親にする指定は 400
- 各変更は従来どおり即 `reclassify_all()` を実行し `reclassified` を返す

### 推奨サブジャンルの投入

`POST /genres/seed-subgenres` を追加する。**起動時の自動投入はしない。**

- `seed_genres` は「`genres` が空のときだけ」走る設計なので、既存環境では子が入らない
- 起動時に自動で投入すると約 15 秒ブロックし、利用者から見れば「勝手に分類が変わった」になる
- 冪等: 既に存在する子キーには触らない。タグの付け替えは **現在そのシードの親ジャンルに属しているタグだけ**を対象にする。既に別のジャンル（利用者が移した先や、そもそも別ジャンルが持っているタグ）にあるものは動かさない。この規則なら「利用者が動かしたのか、まだ投入していないのか」を区別する必要がない
- 戻り値は `{"created": n, "moved": n, "reclassified": n}`

シード表は `genre_seed.py` にデータとして置き、後から別ジャンルの子を足したときに同じボタンで追加分だけが入る。

## フロントエンド

### サイドバー（`FeedSidebar.tsx`）

- 親の `unread_count` が **30 以下なら子を出さない**。現状と同じ 1 行のまま
- 30 を超えたら親行の下に子を字下げして並べる。親行は残すので、まとめて見ることもできる
- 子を持つ親で `direct_count > 0` のときは、子の末尾に「その他」行を出す（クリックで `genre=<親>&genre_exact=true`）
- **選べる束の行**（子・「その他」・子を持たない親）は、件数が 30 を超えたら件数バッジを amber にし、`title` に「子ジャンルを追加すると更に分けられます」を出す
- 子を持つ親の行は集計の見出しなので警告色にしない
- 閾値は `GENRE_SPLIT_THRESHOLD = 30` として 1 箇所に置く

`ArticleFilters` に `genre_exact?: boolean` を追加する。`App.tsx` の各ナビハンドラは互いのフラグを明示的にクリアする作法なので、`genre` をクリアする箇所すべてで `genre_exact` も一緒にクリアする。

### ジャンル管理（`GenreManagerModal.tsx`）

- 一覧を親子の入れ子で表示する
- ジャンル作成時に親を選べる（未選択なら親ジャンル）
- 既存ジャンルの親を変更できる
- タグの移動先の選択肢に子ジャンルを含める

## 初期投入の内容

実データのタグ分布から作る。並び順が優先度（先に定義した子が勝つ）。

**AI・LLM**
- `ai_llm` 「LLM・生成AI」— `llm` `openai` `claude` `chatgpt` `gemini` `genai` `rag` `mcp`
- `ai_misc` 「AI 全般」— `ai`
- `ai_infra` 「AI ハードウェア」— `nvidia`

**開発・技術**
- `dev_prog` 「プログラミング」— `programming` `python` `rust` `javascript` `web` `api` `github` `vscode` `unity`
- `dev_infra` 「クラウド・インフラ」— `cloud` `aws` `linux` `windows` `microsoft` `network`
- `dev_data` 「データ・DB」— `database` `data` `excel`
- `dev_tools` 「ツール・ハード」— `tools` `software` `it` `performance` `hardware`
- `dev_general` 「技術一般」— `technology`（**`is_generic=True` のまま**移す。`GENERIC_SEED` の汎用ルールで、通常ルールが 1 つも当たらないときだけ使われる）

閾値を超えているのは現状この 2 ジャンルだけなので、初期投入もこの 2 つに限る。`politics`（25）や `science`（20）は超えてから足す。

汎用ルールも階層の対象になるため、子孫優先の枝刈りは通常ルール・汎用ルールの各段で行う。

## テスト

- `classify`: 祖先と子孫が両方 hit したら子孫が勝つ / 無関係なジャンル同士は priority で決まる / 子ルールが無いタグは親に落ちる / `other` は従来通り
- genre スコープ: 親指定が子孫を含む / 子指定はその子だけ / `genre_exact` は親直下だけ
- `mark-all-read` と `dismiss` が上と同じ展開を使う（親指定で子の記事も対象になる）
- 件数 API: 親の `unread_count` が `direct_count` + 子の合計になる / 子を持たないジャンルは `children: []`
- ジャンル CRUD: 子を親に指定できない / 自分の子孫を親にできない / 親削除で子も消える
- `seed_subgenres`: 2 回実行しても差分が出ない / 利用者が移したルールを戻さない / 未定義の親には何もしない

LLM は関与しないので、これらは全て LLM モック不要。

## 影響とコスト

- 初回の推奨サブジャンル投入で約 6,400 件が子キーへ動き **約 15 秒**（FTS 再インデックス）。明示ボタンなので待ちは操作者に帰属する
- 以降は子ルールを 1 つ動かすたびに `reclassify_all` が走る既存の慣習通りで、変化した行だけの UPDATE
- `GET /articles/genres` のレスポンス形状が変わる。フロントを同時に更新するため、ビルド済み `dist` の古いバンドルが残っていると子が表示されない（`make deploy` でビルドすること）
- 既存の記事データは変更不要

## 既知の限界

- **上限は保証しない。** 前提 1 の通り、支配的タグを持つジャンルは意味では割り切れない。`AI 全般`（タグ `ai`）は未読が増えると 30 を超えるが、`ai` より細かい AI 系タグが `tag_suggestions` に現れない記事はこれ以上分けられない。`technology` や `security` のような他ジャンルのタグを子ルールに借りることはできない（`GenreRule.tag` はグローバル一意で、借りると元のジャンルから記事が消える）
- 子の粒度は手動で育てる。どのタグを子に置くべきかの提案機能は範囲外

## 棄却した代替案

**日付範囲で自動チャンク**（各束が 30 以下になるよう境界を自動で選ぶ）: 上限を確実に保証でき、境界が動かないので一括操作とも両立し、辞書の手入れも不要。棄却の理由は、束のラベルが日付になり「この話題は今は要らない」という判断ができないこと。ただし上限の保証が必要になったら、子の下にこの方式を足すのが素直な拡張になる。

**フィード（情報源）で分割**: 「このソースの分はまとめていい」がやりやすいが、はてなブックマーク総合のように 1 フィードの中身が雑多な場合に束が意味を持たない。2026-08-08 の設計でフィード単位の一括処理を捨てたのと同じ理由。

**並び順で 30 件ずつ**: 前提 3 の通り、束の中身が新着で変わるため一括操作と両立しない。
