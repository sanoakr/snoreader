# はてなブックマーク由来の重複記事の抑制

- 日付: 2026-09-10
- 状態: 設計合意済み
- 関連: `app/services/deduplicator.py`（URL 正規化・フィード横断 dedup）、`app/services/feed_fetcher.py`

## 目的

はてなブックマーク（`b.hatena.ne.jp/hotentry.rss`、以下「はてブ」）は他サイトの記事を
再配信する引用フィードなので、他フィードと同じ記事が二重に入る。既存の
`dedup_articles()` は URL 正規化キーの完全一致でこれを潰しているが、
それでも読む側には重複が残っている。何が残っているのかを実測し、
残った 3 種類それぞれに対処する。

## 現状の測定（2026-09-10、全 17,218 件 / 保持期間 60 日）

`normalized_url` が完全一致する重複グループは **0 組**。既存 dedup は正しく効いている。
残っているのは以下の 3 種類だった。

| 型 | 内容 | 実測 |
|---|---|---|
| **A** | 同一記事の URL 表記ゆれ（`sp/` ↔ `jc/`、ページ番号、ゴミパラメータ等） | 18 組 |
| **B** | 同じニュースを別媒体が報じた別記事 | 30 組 |
| **C** | 購読済みサイトの記事がはてブ経由でも流れてくる | 408 件 |

フィード別の記事数は はてブ 5,842 / Yahoo 4,584 / GIGAZINE 1,625 / Qiita 1,511 /
ITmedia 1,199 / Zenn 776 / ハムスター速報 595 / AI Watch 465 / テクノエッジ 261 /
大学ジャーナル 207 / Publickey 116 / WirelessWire 37。はてブが最大で、
全体の 34% を占める。

## 全体構成

3 つとも `fetch_all_feeds()` の 1 サイクルの中に収める。新しいスケジュールジョブは作らない。

```
fetch_all_feeds()
  ├─ fetch_feed() × N      ← C: はてブ取り込み時に購読済みホストをスキップ
  ├─ dedup_articles()      ← A: normalize_url 強化（既存フローに乗るだけ）
  ├─ cluster_stories()     ← B: 新規。同一ニュースの別媒体版を代表 1 件に絞る
  ├─ cleanup_old_articles()（既存）
  └─ refresh_split_suggestions()（既存）
```

LLM は一切使わない。3 つとも決定的な関数で、テストが実データを再現できる。

## A — `normalize_url` の表記ゆれ吸収

### 追加する規則

既存の `_TRACKING_PARAMS` / `_DOMAIN_ALIASES` と同じ「実データで確認できたものだけ列挙する」
方針を踏襲する。汎用の推測ルールは入れない。

**1. ドメイン別名**（`_DOMAIN_ALIASES` に 1 行追加）

```
s.japanese.joins.com → japanese.joins.com
```

`m.` `s.` `sp.` の一括除去は**採用しない**。全 17,218 件中この 1 件しか該当がなく、
`m.media-amazon.com` のような無関係ホストを別ホストに潰すリスクの方が大きい。

**2. ホスト別のパス書き換え**（新設 `_PATH_REWRITES: dict[str, list[tuple[pattern, repl]]]`）

| ホスト | 書き換え |
|---|---|
| `jiji.com` | `^/sp/` → `/jc/` |
| `news.livedoor.com` | `^/lite/article_detail/` → `/article/detail/` |
| `nikkansports.com` | `^/m/` → `/`、および `_m\.html$` → `.html` |

`_DOMAIN_ALIASES` を引いた**後**のホストで参照する。

**3. 末尾ページ番号の除去**

```
^(?P<head>/.*/(?P<prev>[^/]+))/(?P<n>[2-9])$
```

にマッチし、かつ `prev` が 1〜2 桁の数字**でない**ときだけ `head` に落とす。

この二重の絞り込みは実測で必要だった。素朴に「末尾の 1〜2 桁の数字セグメントを除去」
とすると `onaji.me/entry/2026/08/18` `…/08/21` `…/08/24` が
`onaji.me/entry/2026/08` に潰れ、**別記事 3 件が 1 件にマージされる**。
`prev` の数字判定は日付パス（`/2026/08/3`）を守るためで、
`[2-9]` 制限は `/10` 以降のページ番号を捨てる代わりに日付の日を守るためのもの。
取りこぼす方向に倒している。

対象の実例: `omocoro.jp/kiji/580351/2/`、`yomiuri.co.jp/local/kyushu/news/20260818-GYS1T00010/2/`

**4. 除去するクエリパラメータ**（`_TRACKING_PARAMS` に追加）

| パラメータ | 出典 |
|---|---|
| `page` | toyokeizai / togetter / dot.asahi / dorachan |
| `timestamp` | querie.me |
| `DETAIL` | news-postseven（値なし） |
| `__readwiseLocation` | Readwise 経由の共有 URL（値なし） |

**5. `p=all`（値限定）**

`p` は汎用的な名前なので**値が `all` のときだけ**除去する（j-cast の全文表示 URL）。

### 効果（実測）

新ルールを全 17,218 件に適用すると **18 組・18 件**が新たに重複として検出され、
**誤爆は 0 件**。うち 1 組（`jiji.com/jc/article?k=2026081200787`）は
`sp/` 版と `jc/` 版で見出しが差し替わっているが、`k=` が同一の同一記事。

跨ぎフィードの例: `qiita.com/Y-Y-dev/items/d526fb7cdbe35a3f9384` が
Qiita フィード（`?utm_*`）とはてブ（`?__readwiseLocation=`）に二重登録されている。

### 反映

`dedup_articles(session, refresh_keys=True)` の既存パスで全件の `normalized_url` を
再計算できる。`main.py` の lifespan にある `normalized_url` バックフィルもこの新ルールで走る。

`share.google/…` の短縮 URL（実データに 2 件）は展開に HTTP フェッチが要るので**対象外**。
`deduplicator.py` 冒頭の「見逃す方向の方が安全」という既存方針に従う。

## C — 購読済みホスト由来のはてブ記事をフェッチ時にスキップ

### 「購読済みホスト」の導出

設定ファイルにもユーザー入力にも持たせず、**保存済み記事から導出する**。
フィードを 1 本足したら自動で追従してほしいため。

> 引用フィード（`_is_hatena(feed.url)`）**以外**の各フィードについて、
> 記事数が **3 件以上 かつ そのフィードの 1% 以上**を占めるホストの集合

実測すると 13 ホストがきれいに出る。

| フィード | ホスト | 占有率 |
|---|---|---|
| AI Watch | `ai.watch.impress.co.jp` | 100% |
| Zenn | `zenn.dev` | 100% |
| Yahoo!ニュース | `news.yahoo.co.jp` | 100% |
| 大学ジャーナル | `univ-journal.jp` | 100% |
| GIGAZINE | `gigazine.net` | 100% |
| テクノエッジ | `techno-edge.net` | 100% |
| Qiita | `qiita.com` | 100% |
| WirelessWire | `wirelesswire.jp` | 100% |
| Publickey | `publickey1.jp` | 100% |
| ITmedia | `itmedia.co.jp` / `monoist.itmedia.co.jp` / `built.itmedia.co.jp` | 92% / 5.3% / 2.8% |
| ハムスター速報 | `hamusoku.com` | 100% |

購読フィードはすべて単一サイト由来で、実データでは非引用フィードのホストは
いずれも 20 件以上あり、少数混入は 1 件も存在しない。二つの下限はどちらも
「たまたま 1 本混ざったホストで、そのサイト全体をはてブから消してしまう」ことを
防ぐためのもの。件数下限を併記するのは、記事数の少ないフィード
（WirelessWire は 37 件）では 1% が 1 件を意味してしまい、割合だけでは
下限にならないため。

**フィード URL のホストから導出する案は採らない**。ITmedia はフィードが
`rss.itmedia.co.jp` で記事が `itmedia.co.jp` なので取りこぼす。

購読していない `pc.watch.impress.co.jp`（はてブに 52 件）や
`forest.watch.impress.co.jp`（45 件）は対象外として正しく残る。

### 適用

引用フィードかどうかの判定は `deduplicator._is_hatena()` を再利用する
（B からも使うので、モジュール公開名 `is_quote_feed()` に改名して 3 か所で共有する）。

`fetch_feed()` の `is_excluded()` 判定の直後。引用フィードのときだけ、
記事 URL のホストが購読済みホスト集合に含まれていたら `continue`。

ホスト集合は 1 フェッチにつき 1 回だけ計算する。`fetch_feed` は
フィード作成・手動リフレッシュからも呼ばれるので、算出は `fetch_feed` の中で
（引用フィードのときだけ）行う。

### 承知の上のトレードオフ

購読フィードは全記事フィードではなく**キュレーション部分集合**（Zenn「トレンド」、
Qiita「人気の記事」、Yahoo「主要トピックス」）なので、はてブにしか出ていない
zenn/qiita/yahoo 記事もこのスキップで失われる。実測 408 件のうち、
購読フィード側に同一記事があるものは A で解消される分だけで、大半は
「購読サイト由来だが購読フィードには載っていない記事」である。

この挙動はユーザーが明示的に選択した（2026-09-10）。実装したのは環境変数
`SNOREADER_SKIP_SUBSCRIBED_HOSTS_IN_QUOTE_FEEDS`（既定 true）と、サイドバーの
フィード ⚙ パネルでの読み取り専用の状態表示（オン/オフと対象ホスト一覧）で、
オン/オフを切り替える UI トグルは持たない。このアプリには実行時に変更可能な
設定ストアがなく、他の挙動系設定（`SNOREADER_ARTICLE_RETENTION_DAYS`、
`SNOREADER_GENRE_UNREAD_LIMIT`）もすべて環境変数のみで管理しているため、
この 1 個の真偽値のためだけに設定テーブルを新設するのは見合わないと判断した。
オフにすれば以降のフェッチから元に戻る（過去分は戻らない）。

### 非表示の実現層

**取り込まない**（DB に入れない）。既存の `ExcludePattern` と同じ層で、
DB が膨らまず、`GET /articles`・ジャンル件数・`mark-all-read`・`dismiss` の
どれにもフィルタ条件が波及しない。

`dismissed_at` を立てる案は採らない。`article_cleanup.py` は dismissed を
削除対象外にしているので、年 2,400 件ペースで永久に溜まる。

## B — 同一ニュースの別媒体版クラスタリング

新規モジュール `app/services/story_clusterer.py`。

### 判定方式

タイトルを記号・空白を除去して正規化し、**文字バイグラム集合の Jaccard 係数**で測る。
閾値 **0.45**、時間窓 **12 時間**、フィード跨ぎのみ。

### タイトル類似度だけでは分離できない（実測）

全件総当たり（±48h、フィード跨ぎ）で閾値を振ると、真陽性と偽陽性の分布が重なる。

```
0.54  [Zenn]  SRE NEXT 2026に登壇・参加してきました
   || [はてブ] SRE NEXT 2026に参加しました｜maru            ← 別人の参加記
0.56  [Zenn]  CyberAgentの追加学習R1をMacで動かしてClineする
   || [はてブ] cyberagent/DeepSeek-R1-Distill-Qwen-32B-Ja  ← 記事とモデルページ
0.43  [Qiita] なぜ、AI時代においてC#は最適な言語の1つなのか？
   || [Zenn]  なぜAI時代にGoが最適な言語なのか                ← 全くの別記事
```

一方、真陽性は 0.40 まで下がってくる（`ドリー・パートン死去` ↔ `米歌手 ドリー・パートンさん死去`）。
**閾値をどこに置いても分離できない。**

分離できたのは**発信主体**だった。偽陽性はすべて UGC / 個人発信のホストが絡んでいる。

### UGC ホストの除外が判定の要

以下のホストを含む記事はクラスタリングの対象外にする（`_UGC_HOST_MARKERS`）。

```
zenn.dev / qiita.com / github.com / note.com / hatenablog / hatenadiary /
speakerdeck.com / anond.hatelabo.jp / togetter.com / posfie.com / medium.com /
dev.to / huggingface.co / x.com / twitter.com / youtube.com / scrapbox.io /
hamusoku.com / blog. / tech. / docs.
```

単純な部分一致ではなく、マーカーの形状によって異なるマッチング規則を適用する。

1. ドット末尾のもの（`blog.` `tech.` `docs.`）: ホストの接頭辞一致（`host.startswith(marker)`）
2. ドットを含むもの（`zenn.dev` `x.com` `youtube.com`）: ホスト完全一致、または
   `.` を挟んだサフィックス一致（`host == marker or host.endswith("." + marker)`）
3. ドットを含まないもの（`hatenablog` `hatenadiary`）: 部分一致（`marker in host`）

単純な部分一致は不採用。`"x.com" in host` では `netflix.com` / `fedex.com` /
`box.com` まで誤って UGC 判定してしまう。

この除外を入れると、閾値 0.45・窓 12 時間で **30 組 / 60 日**、目視での偽陽性は
1 組（テクノエッジの体験レポート ↔ ニュース記事）のみになる。

真陽性の例:

```
0.46  キオクシア 上場来高値から半値に        ↔ キオクシア株、一時ストップ安　上場来高値から半値以下に
0.53  芸術家の草間彌生さん死去               ↔ 【速報】前衛芸術家の草間弥生さん死去
0.68  ニチレイ障害 ハッカー集団が声明        ↔ 【速報】ニチレイ障害、ハッカー集団が犯行声明
1.00  VSCodeのCopilotがAzureの料金から…    ↔ （同一タイトル・別媒体）
```

閾値・窓・UGC リストはモジュール定数にし、**実測値である旨と測定日をコメントに残す**。
「単純化」で UGC 除外を落とすと上の偽陽性が復活するので、その旨も明記する。

### 代表の選択

```
is_saved > 非はてブ由来 > タイトルが長い方 > published_at が早い方 > id が小さい方
```

`dedup_articles` の優先順位に「タイトルが長い方」を挟んだもの。代表が
新規取得側とは限らない — 既存のはてブ記事と新規の元媒体記事がぶつかった場合は、
**既存側（はてブ）を非表示にして新規側を残す**。Yahoo!ニュースの
トピックス見出しは `キオクシア 上場来高値から半値に` のように切り詰められるので、
長い方＝元媒体の記事を残す方が読む価値が高い。

### 非表示の実現層

**`dismissed_at` を立てる**（削除しない）。A・C と違って B の判定はファジーなので、
誤爆を「非表示」ビューで確認して Undo できる状態にしておく。
実測 30 組 / 60 日 ≒ 年 180 件なので、`article_cleanup` が dismissed を
削除しないことによる蓄積は無視できる。

`Article.dismissed_at` の既存セマンティクス（未読のまま隠す、cleanup 対象外、
`GET /articles?dismissed=true` で一覧）にそのまま乗る。新しい列は追加しない。

### 冪等性

候補は**今サイクルで新規取得された記事だけ**に限る（`fetched_at` が
直近 2 時間以内。スケジュールは既定 60 分間隔）。比較対象は直近 12 時間の
`dismissed_at IS NULL` かつ**未読**の記事に限る（`is_read == False`）。保管済みでも
既読なら対象に含めない。既読記事を対象に含めて dismissed を立ててしまうと、
`article_cleanup.py` は dismissed を削除対象外にしているため、その記事は
永久に削除されなくなる（未読のまま隠すという `dismissed_at` の既存セマンティクスとも
噛み合わない）。

これでユーザーが手で非表示を解除した記事を毎時間再び非表示にすることがなくなる
（解除対象が 12 時間窓に残っている間だけ再判定の余地があるが、
新規取得側ではないので候補にならない）。新しい列やテーブルは要らない。

### 計算量

12 時間窓の記事数は実測で数十〜200 件程度。新規取得分 × 窓内の記事の総当たりでも
数千回の集合演算にとどまるので、フェッチサイクルの中で同期実行して問題ない。

## テスト

すべて LLM 非依存。

| ファイル | 内容 |
|---|---|
| `tests/test_deduplicator.py`（追記） | A の各規則。特に **`onaji.me/entry/2026/08/18` 系 3 件が別記事のまま残る**ことを固定するケース（素朴な末尾数字除去への退行を落とす） |
| `tests/test_source_coverage.py`（新規） | C のホスト導出。1% 閾値の境界、引用フィード自身は集合に寄与しない、購読していないホストが混ざらない |
| `tests/test_story_clusterer.py`（新規） | B の真陽性 3 例・上の偽陽性 3 例（UGC 絡み）が**クラスタ化されない**こと、代表選択の優先順位、同じ入力を 2 回流しても追加の非表示が発生しない冪等性 |

## 却下した案

- **B を削除で実装する**: 実測 30 組中 1 組は誤爆で、別媒体の別記事を復旧不能に失う。
  dismissed なら「非表示」ビューで確認できる。
- **B の判定を LLM に投げる**: ジャンル分類を辞書に固定した理由（`genre_classifier.py`）と同じで、
  一括操作の対象は「確実にその条件を満たす集合」でなければならない。1 サイクル数十件の
  LLM 呼び出しコストも、フェッチサイクルに同期で入れるには重い。
- **C を表示時フィルタで実装する**: `GET /articles`・ジャンル件数・`mark-all-read`・
  `dismiss` の全部に条件が波及し、genre スコープと同じ「3 か所が一致していないと壊れる」
  構造を増やす。
- **C の対象ホストをユーザーが手で登録する**: フィードを足すたびに二重管理になる。
- **`m.` `s.` `sp.` サブドメインの一括除去**: 実データで 1 件しか効かず、
  無関係ホストを潰すリスクが上回る。
- **はてブのエントリ URL を `b.hatena.ne.jp/entry/…` として正規化する**: はてブフィードの
  `link` は既に元記事の URL を指しているので、そもそも不要。
